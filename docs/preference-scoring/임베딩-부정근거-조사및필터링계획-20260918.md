# 임베딩 부정 근거 조사 및 필터링 계획 (2026-09-18)

## 0. 결론

현재 임베딩은 후기 문장이 사용자 취향과 **관련 있는지** 찾는 데는 유용하지만,
그 취향을 **추천하는지 반대하는지** 안정적으로 판정하지 못한다.

따라서 임베딩 유사도를 바로 긍정 추천 점수로 해석하면 안 된다. 다음처럼 역할을
나누는 것이 맞다.

1. 임베딩: 취향과 관련된 문장을 검색한다.
2. 방향 판정: 검색된 문장이 긍정 근거인지, 부정 근거인지, 애매한지 판정한다.
3. 추천 점수: 긍정 근거만 가산하고 부정 근거는 긍정 점수에서 제외한다.

첫 구현은 새 모델을 바로 추가하지 않고 **취향 대상과 같은 절에 붙은 강한 부정
표현만 제외하는 보수적인 규칙**으로 시작한다. `불편`, `별로` 같은 단어 하나만
보고 문장 전체를 버리는 규칙은 사용하지 않는다.

## 1. 현재 서비스의 임베딩 검색 방식

현재 추천 취향 검색은 다음과 같이 동작한다.

```text
사용자 취향 발화
  예: "카공하기 좋은 카페"
        ↓
jhgan/ko-sroberta-multitask로 768차원 벡터 생성
        ↓
Supabase에서 후기·블로그 문장 벡터와 코사인 유사도 계산
        ↓
유사도 0.43 미만 제외
        ↓
20자 미만 문장 제외
        ↓
장소별 상위 3개를 긍정 취향 근거처럼 점수에 사용
```

관련 코드:

- 모델과 정규화: `backend/app/providers/place_evidence_encoder.py`
- 유사도 컷과 20자 필터: `backend/app/providers/place_evidence.py`
- 3칸 평균과 0~1 점수 환산: `backend/app/domain/scoring.py`

현재 `place_evidence.py`의 후처리는 길이만 검사한다. 문장의 긍정·부정 방향을
판정하는 로직은 없다.

## 2. 임베딩이 부정문을 자동으로 멀리 보내지 못하는 이유

문장 임베딩은 문장을 벡터 하나로 압축한다. 코사인 유사도는 두 벡터의 방향이
얼마나 가까운지를 계산한다. 이 값은 별도의 `positive`, `negative`, `neutral`
라벨이 아니다.

예를 들어 다음 두 문장은 결론은 반대지만 같은 대상을 매우 많이 공유한다.

```text
카공하기 좋은 카페다.
카공하기 불편한 카페다.
```

두 문장 모두 `카공`, `카페`, `하기`를 포함한다. 임베딩 모델이 부정 표현의 영향을
충분히 크게 학습하지 않았다면 공통된 주제와 문장 구조가 `좋은`과 `불편한`의 차이보다
벡터를 더 강하게 지배할 수 있다.

문장 임베딩 연구에서도 텍스트가 유사하지만 의미가 반대인 부정문을 과도하게 가깝게
평가하는 문제가 보고되어 있다. 이를 개선하기 위해 원문과 부정문을 별도 soft negative로
학습하는 방법도 제안됐다.

- Sentence Transformers STS 문서: https://sbert.net/docs/sentence_transformer/usage/semantic_textual_similarity.html
- SNCSE 논문: https://arxiv.org/abs/2201.05979
- 현재 모델 카드: https://huggingface.co/jhgan/ko-sroberta-multitask

즉, 임베딩은 단순한 키워드 검색보다 문맥을 더 많이 반영하지만 **논리적 함의나
긍·부정을 항상 올바르게 판정하는 분류기**는 아니다.

## 3. 현재 서비스 모델 직접 실측

서비스와 같은 `jhgan/ko-sroberta-multitask`, `normalize_embeddings=True` 조건으로
다음 문장을 직접 측정했다.

질의:

```text
카공하기 좋은 카페
```

| 비교 문장 | 코사인 유사도 | 현재 컷 0.43 통과 |
| --- | ---: | --- |
| 카공하기 좋은 카페 | 1.0000 | 통과 |
| 노트북으로 작업하기 좋은 카페예요. | 0.5255 | 통과 |
| 콘센트가 많아서 카공하기 좋아요. | 0.6100 | 통과 |
| 콘센트 이슈로 카공하기엔 비추합니다. | 0.3852 | 제외 |
| 노트북 사용이 금지된 카페입니다. | 0.2929 | 제외 |
| **카공하기 불편한 카페예요.** | **0.6702** | **통과** |
| 아이와 방문하기 좋은 카페예요. | 0.5955 | 통과 |

### 해석

- 모델이 모든 부정문을 똑같이 놓치는 것은 아니다. 짧은 `비추`, `금지` 예시는
  현재 컷 아래로 내려갔다.
- 그러나 `카공하기 불편한 카페`는 긍정 문장보다 높은 유사도를 받았다. 부정 방향
  판정이 일관되지 않다는 뜻이다.
- `아이와 방문하기 좋은 카페`도 `좋은 카페`라는 공통 표현 때문에 0.5955를 받았다.
  유사도에는 취향뿐 아니라 장소 유형과 문장 틀도 영향을 준다.
- 실제 후기는 짧은 예시보다 길다. 한 문장 안에 `좌석`, `콘센트`, `노트북`, `카공`,
  `카페`, `추천`이 여러 번 나오고 끝에만 `비추`가 붙으면 관련 표현들이 벡터를
  지배할 수 있다.

따라서 `비추`와 `금지`가 포함된 실제 근거의 **전체 저장 문장과 유사도**를 개발자
화면에서 다시 확인해야 한다. 짧은 문구만 떼어 낸 실측과 실제 저장 조각의 값은
다를 수 있다.

## 4. 임베딩이 맡기에 적합한 일과 부적합한 일

| 단계 | 질문 | 적합한 방법 |
| --- | --- | --- |
| 관련성 검색 | 이 후기가 카공 이야기를 하는가? | 임베딩 검색 |
| 방향 판정 | 카공하기 좋다는 뜻인가, 어렵다는 뜻인가? | 대상별 부정 규칙 또는 분류기 |
| 추천 채점 | 이 문장을 긍정 가산점으로 써도 되는가? | 관련성 + 방향 판정 결합 |

`노트북 사용 금지`는 카공 질문에 매우 관련 있는 문장이다. 정보 질문에 답할 때는
중요한 근거지만, 추천 점수의 긍정 가산점으로 쓰면 안 된다. 그러므로 부정 근거는
원문 데이터에서 삭제하는 대신 다음처럼 다루는 것이 좋다.

- 긍정 취향 점수에서는 제외
- 개발자 화면과 향후 주의사항 생성용으로 별도 보존
- 장소를 무조건 제거하거나 즉시 감점하는 것은 다음 평가 후 결정

## 5. 단순 부정 키워드 필터의 오탐 위험 조사

평가 코퍼스 `evaluation_corpus.csv`의 1,500개 문서를 대상으로 `불편`, `비추`,
`별로`, `금지`, `불가`, `안됨`이 포함된 문장을 거칠게 검사했다. 문장 분리는
정규식 기반이고, 긍정 표현 또는 전환 접속어가 함께 있으면 혼합 가능 문장으로
계산했다. 따라서 아래 수치는 정답률이 아니라 **단순 키워드 제외의 위험 범위를
보기 위한 1차 감사 결과**다.

| 표현 | 포함 문장 | 긍정·전환 표현도 함께 포함 | 예시 위험 |
| --- | ---: | ---: | --- |
| 불편 | 52 | 45 | `불편함 없이`, `교통은 불편하지만 부모님 모시기 좋다` |
| 비추 | 19 | 16 | 특정 메뉴만 비추천하거나 추천·비추천 대상을 함께 나열 |
| 별로 | 82 | 55 | `사람이 별로 없어 조용하다`, `산미가 별로 없다` |
| 금지 | 7 | 5 | 금지 규칙을 인용한 뒤 현재는 가능하다고 설명할 수 있음 |
| 불가 | 69 | 46 | `자차 진입 불가지만 대중교통은 편하다`처럼 다른 조건의 부정 |
| 안됨 / 안 됨 | 0 | 0 | 이번 표본에서는 없음 |
| 합계(표현 간 중복 가능) | 222 | 160 | 문장 전체 제외 시 오탐 가능성이 큼 |

실제 발견 사례:

```text
교통편이 생각보다 불편하지만 맛과 분위기만 보면
부모님 모시고 가기에는 더없이 좋은 식당
```

`불편`만 보면 부모님 취향의 강한 긍정 근거까지 삭제하게 된다.

```text
문 아래로 사람이 지나다녀 불편하지 않을까 걱정했는데,
실제로는 사람이 돌아다니는 일이 크게 없었다
```

걱정을 부정한 문장인데도 `불편` 키워드가 있다.

```text
사람이 별로 없어 조용한 분위기를 즐기기 좋았다
```

`별로`는 부정 감정이 아니라 적은 인원을 뜻하고, 조용함에는 긍정 근거다.

따라서 다음과 같은 전역 규칙은 사용하지 않는다.

```python
if any(word in sentence for word in ("불편", "비추", "별로", "금지", "불가")):
    exclude(sentence)
```

## 6. 규칙 기반과 한국어 감정분석 모델 비교

### 6.1 보수적인 규칙 기반 필터

| 항목 | 평가 |
| --- | --- |
| 장점 | 추가 모델·메모리·API 비용이 없고 매우 빠르며, 왜 제외됐는지 설명 가능 |
| 단점 | 우회 표현, 반어법, 긴 문맥을 놓치고 규칙 유지보수가 필요 |
| 주요 위험 | 단어 하나만 보면 혼합 문장과 다른 조건의 부정까지 제거 |
| 적합한 사용 | `노트북 사용 금지`, `카공 비추`처럼 대상과 부정이 같은 절에 있는 고정밀 사례 |

규칙 기반을 쓴다면 **부정 단어 목록**이 아니라 **취향 대상 + 부정 술어 패턴**으로
만들어야 한다.

예시:

```text
(카공|공부|작업|노트북) ... (비추|금지|불가|어렵|불편)
(콘센트|와이파이) ... (없|부족|안 됨|불안정)
(부모님|어르신) ... (비추|불편|어렵|적합하지 않)
```

다음 예외도 부정 판정보다 먼저 처리해야 한다.

```text
불편하지 않다
불편함 없이
금지가 아니다
사용 가능하다
사람이 별로 없다
산미가 별로 없다
```

### 6.2 공개 한국어 감정분석 모델

공개 모델을 `transformers`의 문장 분류 파이프라인으로 붙이는 것 자체는 어렵지
않다. 문제는 코드량보다 **우리 질문에 맞는 라벨을 학습했는가**다.

예시 후보:

- `cringepnh/koelectra-korean-sentiment`: KoELECTRA 약 0.1B, 가중치 약 443MB,
  NSMC 한국어 영화 리뷰의 긍정/부정 이진 분류. 모델 카드 기준 정확도 약 90.5%.
  https://huggingface.co/cringepnh/koelectra-korean-sentiment
- `likeyellow/klue-review-star`: 한국어 식당 리뷰 기반이지만 장소 전체 평가나 별점에
  가깝고, 취향 대상별 판정과는 다르다. 라이선스도 비상업 조건을 확인해야 한다.
  https://huggingface.co/likeyellow/klue-review-star

운영 측면의 차이:

| 항목 | 규칙 기반 | 0.1B 감정분석 모델 |
| --- | --- | --- |
| 모델 메모리 | 추가 없음 | 가중치만 약 443MB, 런타임 메모리는 더 필요 |
| 요청 지연 | 사실상 무시 가능 | 후보 문장을 배치 추론하는 시간 추가 |
| 의존성 | 기존 코드만 | 모델 파일·토크나이저·추론 초기화 필요 |
| 중립 처리 | 규칙에 따라 보존 가능 | 이진 모델은 애매한 문장도 긍정/부정 중 하나로 강제 |
| 도메인 적합성 | 취향별로 직접 설계 가능 | 영화·식당 전체 감정과 여행 취향 적합성은 다름 |
| 설명 가능성 | 어떤 패턴에 걸렸는지 명확 | 확률은 나오지만 대상별 이유는 불명확 |

### 6.3 일반 감정분석 모델만으로 해결되지 않는 핵심 문제

우리가 필요한 것은 문장 전체의 기분이 아니라 **사용자가 요청한 취향에 대한 방향**이다.

```text
커피와 디저트는 훌륭하지만 노트북 사용은 금지되어 있다.
```

일반 감정분석 모델은 전체 문장을 긍정으로 분류할 수 있다. 그러나 `카공하기 좋은
카페`라는 질문에는 명백한 부정 근거다.

반대로 다음 문장은 전체적으로 불평이 있어도 부모님 동행에는 긍정이다.

```text
교통은 불편했지만 음식이 부드럽고 직원이 친절해서 부모님 모시기 좋았다.
```

그러므로 장기적으로 필요한 모델은 단순 감정분석보다 다음 형태의 **대상 기반 판정**이다.

```text
입력: 취향 질의 + 후기 문장
출력: supports / contradicts / unclear
```

이것은 자연어 추론 또는 aspect-based sentiment에 가깝다.

## 7. 권장 구현 계획

### 1단계 — 고정밀 규칙을 먼저 적용

목표는 부정문을 많이 잡는 것이 아니라, **확실한 부정 근거만 긍정 점수에서 빼는 것**이다.

1. 검색 질의에서 취향 코드를 확보한다. 예: `study`, `with_parents`, `quiet`.
2. 후기 문장을 마침표·개행뿐 아니라 `지만`, `는데`, `으나`, `반면`, `다만`,
   `그래도` 같은 전환 표현을 기준으로 절 단위로 나눈다.
3. 같은 절 안에서 해당 취향의 대상어와 강한 부정 술어가 함께 있을 때만
   `hard_negative`로 판정한다.
4. `불편하지 않다`, `불편함 없이`, `금지가 아니다` 같은 부정의 부정과 허용 표현을
   먼저 예외 처리한다.
5. 긍정과 부정이 같은 절에 공존하거나 방향이 불명확하면 `ambiguous`로 남기고
   첫 버전에서는 제거하지 않는다.
6. `hard_negative` 문장은 긍정 `taste_evidence`와 임베딩 평균에서 제외하되,
   원문은 삭제하지 않고 별도 디버그 근거로 보존한다.

중요한 적용 순서:

```text
RPC에서 장소별 유사도 상위 10개 조회
→ 20자 미만 제거
→ 강한 부정 근거 제거
→ 남은 긍정/미확정 문장 중 상위 3개 선택
→ 3칸 평균 계산
```

상위 3개를 먼저 고른 뒤 부정을 빼면 4~10위의 정상적인 긍정 근거를 놓치므로,
반드시 10개 후보 풀에서 부정을 먼저 제거해야 한다.

### 2단계 — 규칙별 테스트 작성

최소 다음 사례를 고정 테스트로 둔다.

| 문장 | 취향 | 기대 판정 |
| --- | --- | --- |
| 노트북 사용이 금지되어 있어요 | study/work | hard_negative |
| 콘센트가 없어 카공하기 불편해요 | study/work | hard_negative |
| 카공하기엔 비추합니다 | study/work | hard_negative |
| 불편함 없이 노트북을 사용할 수 있어요 | study/work | keep |
| 교통은 불편하지만 부모님 모시기 좋아요 | with_parents | keep |
| 커피는 좋지만 카공 장소로는 비추예요 | study/work | hard_negative |
| 사람이 별로 없어 조용해서 좋아요 | quiet | keep |
| 산미가 별로 없고 콘센트가 많아요 | study/work | keep |
| 노트북 금지라는 후기가 있었지만 지금은 가능해요 | study/work | ambiguous/keep |

### 3단계 — 실제 검색 근거 평가셋 구축

임의 문장이 아니라 현재 검색에서 상위로 나온 문장을 사용한다.

- 취향 질문 8~12개
- 지역과 장소 유형을 다양하게 구성
- 검색 상위 근거 약 200~300문장 표본
- 라벨: `support`, `contradict`, `unclear`
- 규칙 평가에서 가장 중요한 지표: `contradict` 판정 정밀도

부정 재현율보다 정밀도를 우선한다. 긍정 근거를 잘못 제거하면 관련 장소가 후보에서
사라지므로, 첫 버전의 hard negative 정밀도 목표는 최소 95%로 둔다.

추천 결과에서는 다음을 함께 측정한다.

- 부정 근거가 최종 Top 5의 긍정 이유로 사용된 비율
- P@5와 nDCG@5
- 장소별 긍정 근거 3칸이 필터 후 얼마나 남는지
- 필터 전후 최종 추천 장소 변화

### 4단계 — 감정분석 모델은 shadow test로 비교

공개 모델을 즉시 순위에 반영하지 않는다.

1. 3단계의 같은 200~300문장을 공개 모델에도 입력한다.
2. 규칙 결과와 모델 결과를 나란히 저장한다.
3. 모델은 부정 확률이 매우 높은 경우만 후보로 표시한다. 예: `negative >= 0.90`.
4. 특히 혼합 문장과 취향 대상이 다른 부정을 따로 평가한다.
5. 규칙보다 명확히 좋아질 때만 온라인 또는 배치 적용을 검토한다.

공개 이진 감정분석 모델은 중립과 대상별 방향을 제공하지 않으므로, 단독 하드 필터로
바로 쓰지 않는다.

### 5단계 — 필요할 때만 대상 기반 분류기로 확장

규칙이 놓치는 간접 표현이 추천 품질에 계속 영향을 줄 때 다음 중 하나를 선택한다.

- 오프라인 적재 시 취향 코드별 `supports/contradicts/unclear`를 미리 계산
- 현재 임베딩 모델 위에 작은 분류 헤드를 학습
- 질의와 근거 문장 쌍을 받는 소형 cross-encoder/NLI 분류기 사용

온라인 추천 요청마다 새 0.1B 모델로 수십~수백 문장을 분류하면 메모리와 지연이
늘어난다. 취향 사전이 정해져 있으므로 가능하면 적재 시 미리 판정해 DB에 저장하고,
온라인에서는 조회만 하는 방식이 유리하다.

## 8. 최종 권고

첫 적용안은 다음과 같다.

```text
임베딩 관련성 검색
→ 취향 코드별 고정밀 부정 규칙
→ hard_negative만 긍정 점수에서 제외
→ mixed/ambiguous는 유지
→ 실제 상위 근거 평가
→ 공개 감정분석 모델은 shadow test
```

단순 키워드 전체 제외는 구현은 쉽지만 실제 코퍼스에서 오탐 위험이 크다. 반대로
공개 감정분석 모델을 바로 추가하는 것은 코드 자체보다 도메인 불일치와 대상별 감정
문제가 더 크다. 현재 단계에서는 보수적인 대상 결합 규칙이 비용·설명 가능성·오탐
통제 측면에서 가장 적절하다.
