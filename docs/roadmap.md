## 지금 진행 중이거나 아직 안 만든 것 (우선순위 순)

### 1. 취향 데이터 모으기 (RAG) — 진행 중, 이 저장소 밖에서

사용자가 "여기 분위기 좋아?" 같은 걸 물었을 때, 블로그 후기나 리뷰를 바탕으로
답해주는 기능을 준비 중이다. 이걸 위해선 먼저 네이버 블로그 글과 구글 리뷰를
모아야 한다.

**지금 상태**: 모은 데이터를 우리 서비스 데이터베이스에 집어넣는 프로그램은
이미 만들어져 있다. 그런데 정작 "모은 데이터" 자체가 이 작업 폴더 안에는 없다
— 담당 팀원이 따로 작업 중인 것으로 보인다. 데이터가 다 모이면 그때 가져와서
연결하면 된다.

주의할 점: 구글 리뷰는 정식으로 데이터를 받는 창구가 없어서 웹사이트를 직접
긁어와야(크롤링) 한다. 사이트 운영 규칙을 지키면서, 너무 자주 접속해서 우리
쪽 IP가 차단당하지 않게 속도 조절이 필요하다.

- 관련 파일: `backend/scripts/import_place_embeddings.py`

### 2. 챗봇 품질 테스트 — 스크립트는 있음, 인텐트별 관리로 전환 예정

챗봇이 잘 대답하는지 확인하는 자동 테스트가 이미 몇 개 있다(질문 종류 분류가
맞는지, 혼잡도 예측이 맞는지, 여러 번 대화를 주고받아도 맥락을 잘 기억하는지
등). thinking_budget(응답 속도 튜닝) 실험 때 만든 속도·정확도 비교표도 있다.

**앞으로 바뀔 것**: 지금은 프롬프트(챗봇이 따르는 지시문)를 인텐트(질문
종류)별로 나눠서 담당자를 정해뒀다. 그래서 테스트도 같은 방식으로 바꾼다 —
**담당자가 자기 담당 인텐트마다 테스트용 질문·정답 세트를 20~50개씩 직접
만들어서 관리**한다. 예를 들어 "장소 비교" 담당자는 "이거랑 저거 어디가
가까워?" 같은 질문 20~50개를 정답과 함께 만들어두고, 프롬프트를 고칠 때마다
그 세트로 다시 돌려서 이전보다 나빠진 게 없는지 확인하는 식이다.

할 일:
- 기존 테스트들을 최신 상태로 다시 돌려서 결과 갱신
- 인텐트별 20~50개 테스트 세트 만들기(담당자별)
- 결과를 표·그래프로 정리해서 발표 자료에 넣기
- (참고) "단계적으로 생각해서 답해"처럼 챗봇에게 사고 과정을 유도하는 프롬프트
  기법(CoT) 실험은 아직 시작 전이다. 지금까지 한 thinking_budget 실험은 이것과
  달리 "AI 모델 내부의 생각 기능을 켜고 끄는" 속도 실험이었다.

- 관련 파일: `backend/scripts/test_*.py`, `backend/test_results/*.csv`

### 3. 상세 카드에 길찾기 버튼 달기 — 아직 안 만듦

장소 상세 카드를 눌러서 열었을 때, 그 안 하단에 "길찾기" 버튼을 하나 단다.
누르면 네이버지도나 카카오맵 같은 지도 앱이 열리면서, **출발지는 현재 내
위치로, 도착지는 그 장소로 자동 입력**돼 있다. 사용자는 앱에서 바로 길찾기
결과만 보면 된다.

이동 시간을 직접 계산해서 추천 순위에 반영하는 건 하지 않는다 — 지도 앱에
연결만 해주고, 실제 경로 계산은 지도 앱한테 맡긴다(비용도 안 들고, 환승
정확도 같은 복잡한 문제도 신경 안 써도 된다).

```
네이버지도: nmap://route/public?slat=(내위도)&slng=(내경도)&dlat=(목적지위도)&dlng=(목적지경도)
카카오맵:   kakaomap://route?sp=(내위도),(내경도)&ep=(목적지위도),(목적지경도)&by=PUBLICTRANSIT
구글맵:     https://www.google.com/maps/dir/?api=1&origin=(내위도),(내경도)&destination=(목적지위도),(목적지경도)
```

지도 앱이 안 깔려 있는 사람을 위해 웹사이트 링크로도 열리게 만들어야 한다.
일정 짜기 기능이 이미 잘 되고 있어서, 나중엔 "다음 장소로 가는 길"도 자연스럽게
이어붙일 수 있다.

- 관련 파일: `app/services/runtime/response_composer.py`, `app/schemas.py`

### 4. 주차 정보 더 채우기 — 아직 안 만듦

지금도 주차 관련 안내가 나오긴 하는데, 이건 관광공사 데이터에 원래 있던 값을
그대로 보여주는 것뿐이다. 
여유가 되면 2단계로, 서울처럼 실시간 주차 정보를 제공하는 지역에 한해 "지금
자리 있음/혼잡"까지 보여줄 수도 있다(전국이 다 되는 건 아니라서 문구를 조심스럽게
설계해야 한다).

- 관련 파일: `app/services/runtime/response_composer.py`, `app/providers/`

### 5. 로그인 만들고, 취향 저장해서 추천에 반영하기 — 절반 진행

로그인 없이도 쓸 수 있게 "게스트로 시작하기" 기능은 이미 만들어져 있다(임시
사용자로 인식하고, 나중에 정식 로그인하면 그 기록을 이어받는 구조까지 설계
완료). **아직 안 된 건, 그 사용자 정보를 대화 기록에 실제로 연결하는 부분**이다
— 담당 팀원 확인을 기다리는 중이다.

이게 끝나면 그 위에 "이 사용자가 예전에 별로라고 한 장소 종류는 다음부터 덜
추천하기"처럼 취향을 반영하는 기능을 얹을 수 있다. 로그인/회원가입 UI 자체를
정식으로 만드는 것도 이 항목에 포함된다.

- 관련 파일: `app/state/schema.py`, `docs/decision-log.md`(D-062, D-063)

### 6. 취향 기반 추천 — 위 1번(취향 데이터)이 끝난 뒤에

1번에서 모으는 리뷰·블로그 데이터가 준비되면, "분위기 좋은 곳", "조용한 곳" 같은
취향 질문에 실제 근거를 가지고 답할 수 있게 만드는 작업. 데이터가 아직 안 모여서
설계는 미루고 있다 — 먼저 설계했다가 나중에 데이터 모양이 바뀌면 다시 만들어야
하기 때문이다.

### 7. 사진 찍어서 장소 물어보기 — 아직 안 만듦

사진을 올리면 "이 장소가 어디인지" 알아보는 기능. Gemini의 이미지 인식 기능을
쓸 수 있을지 확인이 먼저 필요하고, 잘못 알아봤을 때 사용자에게 다시 확인하는
절차도 설계해야 한다.

### 8. 오늘 운영시간만 딱 보여주기 — 아직 안 만듦

지금은 "월~일 요일별 운영시간 + 계절별 예외"가 통째로 길게 나온다. 이걸 "오늘은
몇 시부터 몇 시까지 열어요"처럼 오늘 것만 골라 보여주는 기능이 아직 없다. 공휴일
휴무 여부도 같이 반영하면 좋다. 손이 많이 안 가는 작업이라 심화 항목 중에서는
먼저 해봐도 좋다.

- 관련 파일: `app/services/runtime/info_display.py`

### 9. 알림 보내기 — 아직 안 만듦

"이 장소 문 닫기 30분 전이에요" 같은 알림. 앱에 알림을 보내는 인프라(FCM)부터
갖춰야 해서, 5번(로그인)이 끝난 뒤에 하는 게 순서상 자연스럽다.

## 이번에 새로 추가된 항목

### 10. 혼잡도를 그래프로 보여주기 — 아직 안 만듦

지금은 혼잡도가 "보통", "혼잡" 같은 글자로만 나온다. 이걸 "오전엔 한산, 오후
2시쯤 가장 붐빔"처럼 시간대별 그래프로 보여주는 기능. 이미 시간대별 예측값
자체는 데이터로 갖고 있어서, 프론트에 그래프 그리는 부품만 붙이면 된다. 다만
서울시 실시간 상권 데이터 연동이 지금 다른 팀원이 별도로 작업 중인 것 같으니,
그게 먼저 정리돼야 어떤 데이터로 그래프를 그릴지 정해진다.

### 11. 취향 데이터 수집 확장 — 구별로 나눠서, 성능 좋은 방식 고르기

1번과 이어지는 다음 단계. 팀원마다 서울의 특정 구 하나씩 맡아서, 문장을
컴퓨터가 이해하는 숫자로 바꾸는 방식(임베딩) 몇 가지를 검색 정확도·속도로
비교해보고 우리 서비스에 가장 잘 맞는 걸 고른다.

### 12. LangChain 도입 — 취향 데이터 검색 기능에 먼저 적용 추천

지금 우리 챗봇은 AI 호출을 직접 짜서 쓰고 있고, 이건 지금 규모엔 그게 더
간단해서 의도적으로 그렇게 했다. 다만 "질문 → 관련 문서 찾기 → 답변 만들기"처럼
여러 단계를 이어붙여야 하는 취향 검색 기능(1·11번)에는, 이런 걸 편하게 이어주는
LangChain이라는 무료 도구가 표준처럼 쓰인다. **기존 챗봇 부분은 그대로 두고,
새로 만드는 취향 검색 기능에만 적용하는 걸 추천**한다.

### 13. Langfuse 도입 — 버전 기록을 눈으로 보기 좋게 (서버 준비 필요)

지금도 "어느 프롬프트 버전이 이 답변을 만들었는지"는 우리 데이터베이스에
기록되고 있다. Langfuse는 이 기록을 예쁜 화면으로 보여주는 도구다. 무료로 쓸 수
있는 범위(한 달 5만 건까지)가 넉넉해서 비용 걱정은 없는데, **직접 서버에 설치해서
쓰려면 별도 서버 프로그램(Docker)을 띄워야 한다.** 지금은 파일로 기록만 잘
남겨두는 걸로 충분해서 미루고 있고, 나중에 "한눈에 보는 화면"이 실제로
필요해지면 그때 붙인다.

### 14. 좋아요/싫어요 버튼 → 저장 → 나쁜 답변 찾아서 고치기

챗봇 답변마다 좋아요/싫어요 버튼을 달아서 사용자 반응을 기록해두고, 나중에
"싫어요"가 많이 눌린 답변만 따로 뽑아 분석해서 프롬프트를 개선하는 데
쓴다. 지금은 "어떤 버전이 답했는지"는 기록하지만 "그 답이 좋았는지 나빴는지"는
기록하지 않는다 — 이 기능이 그 빈틈을 채운다.

- 관련 파일: `backend/docs/package-b/llmops-trace-contract-v1.md`,
  `app/state/schema.py`

### 15. AWS에 실제로 배포하기 — 아직 안 만듦, 심화 목표에 포함

지금은 개발자 컴퓨터에서만 돌아가고 있다. 로컬에서 잘 되는 것에서 끝내지 않고,
실제 서비스처럼 인터넷 어디서나 접속할 수 있게 AWS(아마존 클라우드)에 올리는
것까지 심화 목표에 포함한다. 채용 시 "배포까지 직접 해봤는지"를 중요하게 보는
경우가 많아서, 반드시 거쳐야 하는 단계로 못 박아둔다.

### 16. LangChain·LangGraph·Langfuse 같은 AI Agent 도구 사용 경험 남기기 — LangGraph 적용 완료

12번(LangChain)·13번(Langfuse)에 이미 적용 아이디어를 적어뒀는데, 여기에
LangGraph(여러 단계를 거치는 AI 흐름을 짜는 도구)도 후보로 추가한다. 이 세
도구는 채용 공고에 자주 등장하는 이름이다.

**이 중 LangGraph는 실제로 적용을 끝냈다(2026-08-24).** 대화 처리 흐름 전체가
한 함수 안에 1,200줄 넘게 들어 있었는데, 이걸 "단계별 상자와 화살표"로 그린
그림(그래프)으로 옮겼다. 사용자가 보는 화면은 **한 군데도 바뀌지 않았다** —
답변 내용도, 답변이 화면에 나타나는 방식도 그대로다. 바뀐 건 안쪽 구조뿐이다.

- **왜 했나**: 흐름이 한 함수에 뭉쳐 있으면 "이 질문이 어느 길로 갔는지"를
  코드를 끝까지 읽어야 알 수 있었다. 그림으로 옮기면 길이 눈에 보인다.
- **정말 안 바뀌었나**: 같은 질문을 옛 방식과 새 방식으로 각각 돌려서 답변과
  화면 표시 순서가 완전히 같은지 18가지 경우로 대조했다. 전부 같았다.
- **느려지지 않았나**: 요청 하나당 1000분의 1초 정도 늘었다. 실제로는 AI가
  답을 만드는 데 몇 초가 걸리므로 체감되지 않는 수준이다.
- 자세한 판단 근거와 검증 결과: `docs/design/langgraph-adoption.md`, 결정 D-072

LangChain·Langfuse는 여전히 "시간 여유가 있으면" 항목으로 남겨둔다.

### 17. 싫어요 피드백을 추천 품질 테스트 자료로 활용 — 진행 중

좋아요/싫어요 버튼(14번, 완료)에 "싫어요를 누르면 이유와 코멘트를 추가로 남길
수 있는" 기능까지 이미 붙여놨다. 이걸 만든 이유는 기본 프로젝트 최종 발표 때
받은 질문 때문이다 — "취향 관련 추천이 잘 된 추천인지 어떻게 판단하나?
별도 테스트로 검증할 수 있나? 추천 스코어링이 적절한지는 뭘로 채점하나?"
이 질문에 답하기 위해, 사용자가 실제로 싫어요를 누르며 남긴 이유·코멘트를
모아서 "이 추천이 왜 별로였는지"를 실제 데이터로 보여주는 테스트 자료로 쓰기로
했다. 모은 데이터는 다음 발표 자료에도 쓸 예정이다.

- 관련 파일: `backend/app/state/feedback.py`, `backend/app/routes/feedback.py`,
  `frontend/src/components/chat/FeedbackButtons.tsx`

### 18. 트리비가 먼저 말을 걸게 만들기 — 설계만 끝남, 아직 안 만듦

지금 트리비는 검색기에 가깝다. "종로 카페 추천해줘"처럼 필요한 말이 다 들어간
질문에는 잘 답하는데, 사용자가 그냥 힘든 상황을 말하면 — "다리를 다쳤어",
"비 오네", "너무 지쳤어" — 아무것도 하지 못하고 "범위 밖"으로 거절해버린다.
사람이라면 "많이 걸으셨나 봐요, 가까운 데서 좀 쉬었다 갈까요?" 하고 먼저
물어볼 텐데 그걸 못 한다.

이걸 고치려면 세 가지가 필요하다. **첫째, 트리비가 대화를 기억해야 한다** —
지금은 주고받은 말 자체를 저장하지 않아서 "다리 다쳤어 → 많이 다치셨어요? →
그냥 삐끗했어" 같은 3턴 대화가 원리적으로 불가능하다. **둘째, 상황을 말하는
발화가 거절되지 않고 처리 단계까지 도달해야 한다.** **셋째, 트리비가 뭔가를
제안했을 때 사용자가 "응"이라고 말로 수락할 수 있어야 한다** — 지금은 버튼을
누르는 방법밖에 없다.

주의할 점이 두 가지 있다. 하나는 **못 하는 걸 제안하면 안 된다**는 것이라,
제안 가능한 목록은 코드에 고정하고 AI에게는 이름만 알려주기로 했다. 다른 하나는
**제안을 너무 자주 하면 오히려 귀찮아진다**는 것이라, 한 번에 하나만 권하고
거절당한 제안은 같은 세션에서 다시 하지 않기로 했다.

약국·다이소 같은 생활 편의 시설 검색은 가장 그럴듯한 예시지만 **이번 범위에서
뺐다.** 지금 장소 검색이 관광 데이터로만 되어 있어 실제로 못 하기도 하고,
"우리는 갈 만한 곳을 찾아주는 서비스지 길안내나 상권 분석 서비스가 아니다"라고
이미 정해둔 방향과 부딪히기 때문이다. 다만 여행 중 돌발상황 해결이라는 관점에서
보면 차별화 기능이 될 수 있어서, "안 한다"가 아니라 **따로 한다**로 남겨뒀다.

자세한 설계는 [대화층 설계 문서](design/conversational-layer.md)에 있다.

- 관련 파일: `backend/app/prompts/router/`, `backend/app/state/schema.py`,
  `backend/app/services/interpret/state_transform.py`
