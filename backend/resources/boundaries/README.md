# 서비스 지원 지역 경계

MVP 지원 범위 밖의 위치를 판정하는 데 쓰는 폴리곤이다.

| 파일 | 내용 |
| --- | --- |
| `seoul.geojson` | 서울 25개 구 경계 (FeatureCollection, 좌표 5,491개, 214KB) |

**지원 구는 이 파일이 아니라 `app/service_area.py`의 `SUPPORTED_DISTRICTS`가 정한다.**
파일에는 25개 구가 다 들어 있고, 그중 목록에 있는 구만 읽어서 판정한다.

## 왜 지원 구만 담지 않고 25개를 다 담는가

지원 구를 늘릴 때 파일 작업을 없애기 위해서다. 구별로 파일을 두면 구를 늘릴 때마다
추출 스크립트를 돌려 파일을 하나 더 만들어야 하는데, 25개를 미리 담아 두면
`SUPPORTED_DISTRICTS`에 한 줄을 더하는 것으로 끝난다.

미리 담는 비용은 사실상 없다 — 전체 214KB, 파싱 2.5ms이고 프로세스당 한 번만 읽는다.
지원 구 4곳만 담았을 때가 30KB였으니 184KB가 늘어난 셈이다.

파일에 있는 구를 전부 지원하는 방식은 쓰지 않는다. 지원 범위는 팀이 합의하는 결정이라
코드에 드러나고 리뷰를 거쳐야 한다. 목록에 있는데 파일에 그 구가 없으면 첫 판정에서
예외로 끊는다.

## 코드 체계 주의

파일 안의 `properties.code`(11010 등)는 **KOSTAT 코드**이고 TourAPI `lDongSignguCd`
(110 등)와 다른 체계다. 판정 코드는 TourAPI 쪽만 쓴다 — `SUPPORTED_DISTRICTS`의
`district_code`가 그것이다. 파일 안의 code는 출처 추적용으로만 남겨 둔다.

폴리곤은 이름(`properties.name`)으로 찾는다. `SUPPORTED_DISTRICTS`의 `name`이 파일의
이름과 정확히 같아야 하고, 다르면 예외로 끊긴다.

## 출처와 라이선스

- 원자료: KOSTAT 센서스용 행정구역경계 (통계청 SGIS)
- 경유: <https://github.com/southkorea/southkorea-maps> — `kostat/2018/json/skorea-municipalities-2018-geo.json`
- 라이선스: `KOSTAT: Free to share or remix.`
- 기준 연도 2018, 추출일 2026-08-24

같은 내용을 파일 최상위 `attribution` 멤버에도 넣었다. 데이터와 출처가 떨어지면 나중에
어느 쪽이 근거인지 추적할 수 없어서다. GeoJSON은 최상위 임의 멤버를 허용한다.

## 왜 역지오코딩이 아니라 폴리곤인가

네이버 Reverse Geocoding은 별도 구독 상품이라 현재 키로는 403이 돌아온다. 구독하더라도
판정 하나 때문에 모든 요청에 외부 호출과 장애 지점을 하나 더 얹게 된다. 행정구역 경계는
거의 변하지 않는 정적 데이터라 매 요청 API로 물어볼 성질이 아니다.

경계 상자(bounding box)는 종로구가 남북으로 길쭉하고 북악산 쪽으로 굽어 있어 맞지 않는다.
지원 구가 늘어도 상자를 합치면 인접 미지원 구(마포·서대문·동대문·광진)가 딸려 들어오는
문제는 그대로다.

## 정밀도

지원 구 네 곳의 폴리곤 면적을 공식 면적과 대조하면 전부 1% 이내다. 추출 스크립트가
돌 때마다 이 대조를 출력하고, `tests/test_service_area.py`도 같은 것을 검사한다.

| 구 | TourAPI 코드 | 좌표 수 | 면적(계산) | 공식 면적 | 차이 |
| --- | --- | ---: | ---: | ---: | ---: |
| 종로구 | 110 | 194 | 24.01 km² | 23.91 km² | +0.40% |
| 중구 | 140 | 188 | 10.04 km² | 9.96 km² | +0.80% |
| 용산구 | 170 | 180 | 21.80 km² | 21.87 km² | −0.32% |
| 성동구 | 200 | 167 | 16.81 km² | 16.85 km² | −0.23% |

활성 장소 2,570건(2026-08-24 기준)의 좌표를 판정했을 때 밖으로 나온 것은 4건이다(0.16%).

| 구 | 활성 장소 | 폴리곤 밖 | 비율 |
| --- | ---: | ---: | ---: |
| 종로구 | 842 | 1 | 0.12% |
| 중구 | 892 | 1 | 0.11% |

| 장소 | 등록 구 | 원인 |
| --- | --- | --- |
| 북악산 숙정문 | 종로구 | 2018년 경계의 정밀도 한계. 북악산 능선 경계에 붙어 있다 |
| 청계8경 버들습지 | 성동구 | 2018년 경계의 정밀도 한계. 청계천 경계에 붙어 있다 |
| 서울어텀페스타 개막행사 | 중구 | 등록 구가 틀렸다. 주소가 "광진구 자양동"이고 좌표도 광진구다 |
| 성촌공원 | 용산구 | 좌표가 깨졌다. (19.694, 117.993)은 남중국해다 |

(D-044). 뒤의 두 건은 폴리곤을 고쳐도 해결되지 않는 원본 데이터 문제다.

## 지원 구를 늘릴 때

경계·판정 쪽에서 할 일은 **한 줄뿐이다.**

```python
# app/service_area.py
SUPPORTED_DISTRICTS = (
    ...
    ServiceDistrict("230", "동대문구"),   # TourAPI lDongSignguCd, 경계 파일의 이름
)
```

`tests/test_service_area.py`의 25개 구 대표점 테스트가 이 목록을 따라 저절로 바뀌므로
테스트도 손댈 필요가 없다. 다만 **그 구의 실제 랜드마크 좌표를 `_INSIDE`에 몇 개 넣고,
새로 인접하게 되는 미지원 구의 좌표를 `_OUTSIDE`에 넣는 것은 권한다** — 대표점은 구
한가운데라 경계가 잘못돼도 안 걸린다. 공식 면적 표(`_OFFICIAL_AREA_KM2`)에도 그 구를
넣는다.

경계·판정 밖에서 별도로 해야 하는 일은 다음과 같고, 이쪽은 구마다 사람이 붙어야 한다.

| 할 일 | 어디서 |
| --- | --- |
| TourAPI 목록·상세 적재 | 개발자 Ops 패널의 장소 동기화. 장소 수만큼 `detailIntro2`를 쓰므로 일일 한도(1,000회)를 확인한다 |
| 집중률 매핑 구축 | 서울시 실시간 도시데이터 제공 지역과 대조해야 한다 |
| 취향 근거 임베딩 | 리뷰 수집→정제→임베딩→적재 (TP-113 방식) |

활성 장소가 늘면서 함께 확인해야 하는 상한도 있다.

| 상한 | 현재 값 | 어디 |
| --- | --- | --- |
| 저장소 페이지 크기 | 1,000 | `repositories/supabase_places.py` `_READ_PAGE_SIZE` |
| 취향 근거 후보 상한 | 500 | 같은 파일 `_MAX_EVIDENCE_CANDIDATES` |
| TourAPI `detailIntro2` 일일 한도 | 1,000회 | 적재 시 |

## 경계 파일 갱신

`scripts/extract_district_boundaries.py`가 원본에서 한 시도의 구를 전부 뽑는다. 전체
파일은 17MB라 저장소에 넣지 않고 스크립트가 URL에서 받는다.

```bash
cd backend

python -m scripts.extract_district_boundaries --extracted-at 2026-08-24

# 파일을 쓰지 않고 구 수·좌표 수·면적만 확인한다
python -m scripts.extract_district_boundaries --extracted-at 2026-08-24 --dry-run

# 내려받아 둔 원본을 쓴다
python -m scripts.extract_district_boundaries --extracted-at 2026-08-24 --source ~/muni2018.json
```

스크립트는 `SUPPORTED_DISTRICTS`의 구가 추출 결과에 다 있는지 확인하고, 없으면 파일을
쓰지 않고 끊는다. 행정구역이 개편되면 `--base-year`를 바꿔 다시 돌린다.
