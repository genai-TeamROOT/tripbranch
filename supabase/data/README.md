# 장소 스냅샷 자료

TourAPI 목록 조회 결과를 구 단위로 떠 둔 CSV와, 그 대조 결과다. DB 동기화 전에
"이번에 무엇이 바뀌는가"를 파일로 남기는 것이 목적이라 git이 추적한다.

## 파일 이름

```
places_api_snapshot_<지역>-<구>_<날짜>[_db].csv
places_reconciliation_<지역>-<구>_<날짜>.csv
```

- `<지역>-<구>`는 TourAPI 법정동코드다(`lDongRegnCd`-`lDongSignguCd`). 종로구는
  `11-110`, 중구는 `11-140`, 용산구는 `11-170`. 코드 표는
  `backend/resources/tour_api/tour_api_ldong_codes.json`에 있다.
- **구를 날짜 앞에 둔다.** 구가 이름에 없으면 같은 날 두 구를 대조할 때 뒤엣것이
  앞엣것을 덮어쓰고, 기준 스냅샷도 다른 구 것을 집는다. 2026-08-20에 중구를
  종로구 스냅샷과 대조해 "삭제 844건"이 나온 사고가 그것이다 — 그 844건은
  폐업이 아니라 전부 종로구 장소였다.
- 날짜가 뒤에 있어 같은 구 안에서는 이름순이 곧 날짜순이다. 기준 스냅샷 탐색이
  그 순서에 기댄다.
- 구가 없는 옛 이름(`places_api_snapshot_20260810.csv`)은 기준 탐색 glob에
  걸리지 않는다. 남아 있어도 "기준 없음"이 될 뿐 다른 구와 섞이지는 않는다.

## 기준이 없는 구를 처음 채울 때

스냅샷이 없는 구는 첫 대조에서 전량이 신규로 잡혀, 이미 DB에 있는 장소에
`detailIntro2`를 한 번씩 더 쓴다(용산구 486건이면 하루 한도 1,000회의 절반이다).
그래서 `places` 테이블에서 읽어 기준을 한 번 세운다. 외부 호출은 없다.

```bash
cd backend
python -m scripts.snapshot_places_from_db --district-code 170
```

파일 이름은 API 스냅샷과 같은 규칙을 쓴다. 이 경로는 기준이 없는 구에 한 번
기준을 세우려고 있는 것이고, **다음 대조부터는 TourAPI 응답이 같은 자리에
들어온다.** 재구성본은 활성 장소만 담는다 — 비활성은 목록에서 사라져서 비활성이
된 것이라, 넣으면 대조할 때마다 계속 "삭제"로 잡힌다.

날짜는 실행일이 아니라 그 구의 `list_fetched_at` 최댓값이다. 자료가 실제로 언제
것인지를 이름이 말해야 한다.

주의: 재구성한 날 같은 구를 대조하면 이름이 겹쳐 그 파일을 덮어쓴다. 대조는
자기가 쓸 파일을 기준 후보에서 빼므로, 그날은 기준이 없는 것과 같아진다. 다음
날부터는 겹치지 않는다.

재구성본이 API 응답과 같은지는 한 번 실측했다 — 2026-08-20 중구 892건을 같은 날
TourAPI 스냅샷과 대조하니 비교 대상 14개 열 전부에서 차이 0건이었다. 한 구 한
번의 측정이므로 "차이가 날 수 없다"가 아니라 "이 경로에서는 안 났다"로 읽는다.

## 몇 개를 남기는가

Ops 패널의 **스냅샷 보관** 절에서 정리한다. 구별로 최근 몇 개만 남길지 정하고,
지울 파일을 미리 본 뒤 `PRUNE`을 입력해 실행한다. 기본값은 **구별 2개**다.

1개만 남기면 **같은 날 두 번째로 대조할 때 기준을 잃는다** — 파일명이 날짜라 첫
대조가 만든 파일을 덮어쓰고, 남은 것이 그것뿐이면 `find_baseline`이 빈손으로
돌아와 `places` 재구성 기준으로 떨어진다. 그래서 화면은 0을 받지 않고, 서버도
`keep < 1`이면 아무것도 지우지 않는다.

정리는 대조·반영에 붙이지 않고 버튼으로 둔다. 대조 직후에 지우면 **반영하지 않은
구의 변경분이 사라진다** — 대조는 DB를 바꾸지 않으므로, 옛 스냅샷을 지우면 다음
대조가 오늘 스냅샷을 기준으로 삼아 오늘 잡힌 신규가 다시는 나오지 않는다. 반영
직후에 지워도 문제가 남는다: 상세조회 상한이 걸린 실행은 비활성화를 건너뛰어
사라진 장소가 DB에 활성인 채 남는데, 스냅샷에는 그 장소가 없어서 다음 대조에서
"삭제"로도 잡히지 않는다.

## 대조 결과 CSV는 반영이 끝나면 지워진다

`places_reconciliation_*.csv`는 **파생물이다.** 스냅샷 두 개를
`build_reconciliation_rows()`에 넣으면 같은 내용이 다시 나오고, 외부 호출도 DB
조회도 없다. 어떤 코드도 이 파일을 읽지 않는다 — 반영은 스냅샷과 화면이 넘긴
`detail_content_ids`만 쓴다.

그래서 반영이 끝나면 그 구의 대조 CSV를 자동으로 지운다. 변경분이 DB에 들어갔으니
파일로 들고 있을 이유가 없다. 되짚어야 할 때는 git에서 꺼낸다.

지우지 않는 경우가 셋 있다.

- `dry_run`: DB에 아무것도 안 썼다.
- **상세조회 상한이 걸린 실행**: 비활성화를 건너뛰므로 대조가 찾은 "삭제" 행이
  반영되지 않은 채 남는다. 그 기록을 지우면 무엇이 남았는지 알 방법이 없다.
- 반영이 `failed`로 끝난 경우.

`partial_failure`는 지운다. 한도 소진으로 상세를 일부 못 채운 것이고, 대조 CSV가
담는 목록 단위 변경은 이미 반영됐다.

그래서 이 디렉터리에 남은 대조 CSV는 **대조만 하고 반영하지 않은 구**의 것이다.
Ops 패널의 정리 버튼이 그 잔여분을 스냅샷과 같은 개수로 함께 치운다(체크로 끌 수
있다).

2026-08-29에 22개 구를 손으로 정리하며 8개 파일을 지웠다(종로구 5개,
중구·용산구·은평구 각 1개). 지운 파일은 git 이력에 그대로 있어
`git show <커밋>:supabase/data/<파일명>`으로 되찾을 수 있다.

광진구(215)·구로구(530)·금천구(545)는 스냅샷 파일이 아직 없다. 이 구들의 첫
대조는 `places` 재구성으로 기준을 세운다.

## snapshot-history.md

대조·반영·정리가 일어날 때마다 한 줄씩 붙는 갱신 이력이다. 어떤 코드도 이 파일을
읽지 않는다 — 대조의 입력은 스냅샷 CSV이고 여기 적힌 것은 그 결과의 요약이라,
이력에 남겼다는 사실이 스냅샷을 지워도 된다는 근거가 되지는 않는다.

**반영도 한 줄로 남긴다.** 대조만 하고 반영하지 않은 구가 생기기 때문이다(전 구
순회는 일일 한도를 넘길 구를 건너뛴다). 대조 줄만 있으면 "이 변경이 DB에 실제로
들어갔는가"를 이력으로 답할 수 없다.

정리 줄에는 지운 파일명이 그대로 들어간다. 되찾는 근거는 이력이 아니라 git이지만,
어느 커밋을 뒤질지는 이 표가 알려준다. 실제로 지워진 파일만 적으므로, 지우다
실패한 파일은 이력에 없다.

## backups/

되돌릴 근거가 필요한 작업 전에 `backups/<날짜>_<사유>/`에 덤프를 남긴다. 그 안의
파일은 이 이름 규칙을 따르지 않는다 — 당시 이름 그대로 보존한다.
